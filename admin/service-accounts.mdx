---
title: "Service Accounts for CI/CD and API Automation"
description: "Create and manage service accounts in Lightdash to authenticate CI/CD pipelines, automated scripts, and API integrations without using personal credentials."
---

Service accounts give non-human callers — CI/CD pipelines, deployment scripts, content-as-code workflows — a dedicated identity to authenticate against the Lightdash API. Unlike a personal access token, which acts as a specific human user, a service account is its own identity with its own role. This means you can scope it to exactly the permissions your automation needs, revoke it independently of any human user, and track activity back to the pipeline rather than to an individual.

## What service accounts are

Each service account consists of:

- A **bearer token** (prefixed `ldsvc_`) used to authenticate API calls
- A **role** that controls what the service account can do
- An **identity** that appears in audit logs and on content created through the service account

Service accounts appear as "Created by [service account name]" on dashboards, charts, and schedulers they create. They are filtered out of human-facing member lists, share pickers, and SCIM user feeds — they are invisible to end users.

## Creating a service account

Only organization admins can create service accounts.

<Steps>
  <Step title="Open the Service Accounts settings">
    Go to **Settings → Organization → Service Accounts** and click **Create service account**.
  </Step>
  <Step title="Enter a description">
    Give the service account a descriptive name that identifies the system or workflow it represents — for example, `CI deploy bot` or `dbt Cloud sync`. This name appears in audit logs and as the content author for anything the service account creates.
  </Step>
  <Step title="Set an expiration date (recommended)">
    Choose a future expiration date. After this date the token is automatically rejected and the service account can no longer authenticate. You can set no expiration, but this is discouraged for long-lived deployments — a leaked non-expiring token has no automatic revocation.
  </Step>
  <Step title="Choose a role">
    Select the role that defines what the service account can do. See [Service account roles](#service-account-roles) below for the options.
  </Step>
  <Step title="Copy the token">
    After clicking **Create**, the token is shown **once**. Copy it immediately and store it securely (for example, as a CI secret or in a secrets manager). Lightdash never shows the token value again — if you lose it, you must delete the service account and create a new one.
  </Step>
</Steps>

<Warning>
  The token is displayed only at creation time. If you close the dialog without copying it, there is no way to retrieve it. Delete the service account and create a new one.
</Warning>

## Service account roles

When creating a service account you choose one of the built-in role tiers or a custom role (enterprise).

### Built-in role tiers

These tiers correspond to the same system roles available to human users:

<Accordion title="system:viewer">
  Read-only access. Equivalent to a human user with the Viewer organization role. Use this for integrations that only need to read dashboards or chart data.
</Accordion>

<Accordion title="system:interactive_viewer">
  Can run queries, explore data, and create scheduled deliveries. Equivalent to the Interactive Viewer organization role.
</Accordion>

<Accordion title="system:editor">
  Can create, edit, and delete spaces, dashboards, and charts. Equivalent to the Editor organization role.
</Accordion>

<Accordion title="system:developer">
  Can deploy projects, use the SQL runner, write content-as-code, manage virtual views, and access source code. This is the recommended tier for most CI/CD pipelines that deploy dbt project changes or upload dashboards-as-code.
</Accordion>

<Accordion title="system:admin">
  Full organization access. Equivalent to the Admin organization role. Use only when the automation genuinely requires admin-level operations such as managing users or creating production projects.
</Accordion>

<Tip>
  For most CI/CD use cases — compiling dbt projects, deploying previews, uploading content-as-code — `system:developer` is the right choice. It covers `manage:DeployProject`, `manage:ContentAsCode`, the SQL runner, and preview project creation without granting user management or project deletion powers.
</Tip>

### Custom roles (enterprise)

If none of the built-in tiers fit your use case, you can assign a custom role. Custom roles let you pick exactly which permission scopes the service account holds — for example, a role that can only deploy projects and upload content-as-code, nothing else.

Custom roles must be created under **Settings → Custom roles** before they can be assigned to a service account. See [Managing Users, Roles, and Groups](/admin/user-management#custom-roles) for how to build a custom role.

## Authenticating with a service account token

Use the `Authorization: Bearer` header with the `ldsvc_` token on every API request:

```bash
curl https://your-lightdash.example.com/api/v1/org/projects \
  -H "Authorization: Bearer ldsvc_your_token_here"
```

```python
import requests

response = requests.get(
    "https://your-lightdash.example.com/api/v1/org/projects",
    headers={"Authorization": "Bearer ldsvc_your_token_here"},
)
```

```javascript
const response = await fetch(
  "https://your-lightdash.example.com/api/v1/org/projects",
  {
    headers: { Authorization: "Bearer ldsvc_your_token_here" },
  }
);
```

<Note>
  Service account tokens use the `ldsvc_` prefix. Personal access tokens use the `ldpat_` prefix. SCIM tokens use the `ldscim_` prefix. The auth middleware rejects a token with the wrong prefix for its intended endpoint.
</Note>

### Using the Lightdash CLI with a service account

The Lightdash CLI accepts a service account token via the `--token` flag or the `LIGHTDASH_API_KEY` environment variable:

```bash
export LIGHTDASH_API_KEY=ldsvc_your_token_here
export LIGHTDASH_URL=https://your-lightdash.example.com

lightdash deploy --project your-project-uuid
```

```yaml
# GitHub Actions example
- name: Deploy to Lightdash
  env:
    LIGHTDASH_API_KEY: ${{ secrets.LIGHTDASH_SERVICE_ACCOUNT_TOKEN }}
    LIGHTDASH_URL: https://your-lightdash.example.com
  run: lightdash deploy --project ${{ vars.LIGHTDASH_PROJECT_UUID }}
```

## Viewing and managing service accounts

All service accounts in your organization are listed under **Settings → Organization → Service Accounts**. The list shows each account's name, creation date, expiration date, and last-used timestamp. Token values are never shown after creation.

From this list you can:

- See when a token was last used (useful for identifying stale service accounts)
- Delete a service account to immediately revoke its access

## Revoking and rotating tokens

### Revoking a token

Delete the service account from **Settings → Organization → Service Accounts**. The token is rejected immediately on the next API call. Content the service account created (dashboards, charts, scheduled deliveries) is not deleted — it is preserved and continues to show the service account's name as the author.

### Rotating a token

There is no in-place token rotation. To rotate:

<Steps>
  <Step title="Create a new service account">
    Create a new service account with the same role and description as the one being rotated.
  </Step>
  <Step title="Update your consumers">
    Update the secret in your CI environment, secrets manager, or automation config with the new token.
  </Step>
  <Step title="Verify the new token works">
    Run your pipeline or automation once to confirm the new token authenticates correctly.
  </Step>
  <Step title="Delete the old service account">
    Once you've confirmed the new token is in use, delete the old service account to invalidate the old token.
  </Step>
</Steps>

<Tip>
  Set a calendar reminder when you create a service account with an expiration date. Tokens expire silently — the next request simply returns a 401. Proactive rotation before expiry avoids unexpected CI failures.
</Tip>

## Token expiration

When a service account token reaches its expiration date, all subsequent API calls return `401 Unauthorized`. There is no grace period and no automatic renewal. Create a new service account and update your consumers before the expiration date.

To check expiration dates, visit **Settings → Organization → Service Accounts** and review the **Expires** column.
